# ADR-039: Flash 启动（FSBL + RISAF 编程 + XSPI 冷启动）

## Phase

P2（存储/启动，承接 ADR-018/019；同时解锁 P4 的 029/032/036）

## 目标

> GitHub Issue: 待建
> 验证级别: MEASURED

让真机从板载 XSPI NOR flash **掉电持久冷启动**到 NSH，脱离 DEV boot 的
SRAM+GDB 加载依赖；并借自定义 FSBL 编程 RISAF，授予 GPDMA1/DMA2D/NPU
对 SRAM 的访问权，解锁被内存防火墙卡住的 ADR-029/032/036。

## 上下文

### 当前限制

P0 起全程 **DEV boot（BOOT1=0,BOOT0=1）**：固件由 GDB 加载到 SRAM
`0x34000400`，掉电即丢，无法独立上电启动——不满足最终产品形态。

同时，DEV boot 下 ROM 的默认 **RISAF** 策略只授权 CPU 的 CID 访问 SRAM，
未授权总线主 DMA 引擎，导致三个 ADR 卡在 PARTIAL：

- **ADR-029 ADC**：GPDMA1 写 SRAM 被防火墙丢弃（轮询模式 MEASURED，DMA 延后）
- **ADR-032 DMA2D**：DMA2D 写 SRAM 被丢弃（探针 MEASURED，填充/搬运延后）
- **ADR-036 NPU**：Neural-ART 读写 SRAM 大概率同样被丢（未验证）

### RISAF 是什么

**RISAF = RIF Security Attribute Firewall**，STM32N6 **RIF（Resource
Isolation Framework，资源隔离框架，RM0486 §7.4）** 的内存防火墙组件。RIF 含：

| 组件 | 全称 | 管辖对象 |
|------|------|----------|
| RIFSC | RIF Security Controller | 外设属性（RISUP 从设备侧、RIMC 主设备 CID 分配） |
| **RISAF** | RIF Security Attribute Firewall | **内存/地址空间**访问控制（AXI SRAM、XSPI 等） |
| RISAL | 轻量版 RISAF | 部分内部小内存 |

RISAF 对**每一笔总线事务**按地址匹配 region，再按发起者的 **CID
（Compartment IDentifier，隔离域标识）**、安全/特权属性、读写方向校验；
CID 不在该 region 授权列表 → 拦截（总线错误或静默丢写）。CPU、GPDMA1、
DMA2D、NPU 各有独立 CID。

正常产品由 **FSBL 在启动早期编程 RISAF**（`HAL_RIF_RISAF_ConfigBaseRegion`
等）把这些总线主 CID 授权进来。ST 预编译 FSBL 把 `HAL_RIF_MODULE_ENABLED`
注释掉了 → 没做这步 → 所以要么自写 FSBL 补上，要么验证 flash-boot 默认
策略是否本就更宽松。

DS14791 Section 6: Boot modes；UM3234: boot ROM；RM0486 §7.4: RIF/RISAF。

## 决策

分阶段推进，先证伪最大未知再决定 FSBL 复杂度：

1. **阶段 0 — RISAF 默认策略探针（低成本，先做）**：
   flash-boot ROM 默认 RISAF 是否和 DEV boot 一样严？UM3234 Table 4 只记录
   DEV boot 的 "Clear RISAF2"，flash-boot 分支未文档化。用最小固件在 flash
   boot 下探测：若默认更宽松，DMA/NPU 到 SRAM 可能免 FSBL 直接可用；若一样
   严，则必须走阶段 2 的自定义 FSBL。**这一步决定后续工作量，必须先做。**

2. **阶段 1 — 最小 flash-boot 打通**：
   物理跳线切 `(BOOT1=0,BOOT0=0)`；复用/裁剪 ST FSBL 初始化 XSPI1 + 内存
   映射；NuttX 固件写入 flash；ROM→FSBL→NuttX 冷启动到 NSH；掉电重启不丢。

3. **阶段 2 — 自定义 FSBL 编程 RISAF（仅当阶段 0 证实需要）**：
   打开 `HAL_RIF_MODULE_ENABLED`，用 `HAL_RIF_RISAF_ConfigBaseRegion` /
   `ConfigSubRegion` / RIMC 授予 GPDMA1/DMA2D/NPU 的 CID 对 SRAM region 的
   读写；回归 ADR-029/032/036 的 DMA/NPU→SRAM 路径至 MEASURED。

4. **阶段 3（可选）— OTA/双分区**：固件持久后再叠加，本 ADR 不含。

### 安全性与砖机风险（低，可逆）

- 芯片出厂 **CLOSED_UNLOCKED**（UM3234 Table 3）：flash 启动**不需签名、
  不需烧 OTP/BSEC 熔丝**，全程可逆。
- flash 写坏可由 `(BOOT1=1,BOOT0=0)` 串口/USB DFU 启动（`.stldr` 外部加载器）
  无条件恢复重刷——**不会变砖**，是迭代出错的安全网。

## 设计

### 启动链变更

```
DEV boot (当前):
  ROM → (BOOT0=1) → SRAM @ 0x34000400 (GDB load) → _stext → nx_start()

Flash boot (本 ADR):
  ROM → (BOOT0=0,BOOT1=0) → FSBL @ flash
    → XSPI1 init + memory-mapped
    → [阶段2] RISAF 编程: 授权 GPDMA1/DMA2D/NPU CID 访问 SRAM
    → jump NuttX (@ SRAM 或 XIP) → _stext → nx_start()

砖机恢复:
  (BOOT1=1,BOOT0=0) → 串口/USB DFU → STM32_Programmer_CLI + .stldr 重刷
```

### 开发/调试代价权衡

| 维度 | DEV boot（当前） | flash boot |
|------|------------------|------------|
| 固件下发 | GDB load SRAM，秒级 | 写 flash ~10–30s（20–50× 慢） |
| SWD 调试 | 直接 attach | FSBL 跑完后仍可 attach，断点/单步保留 |
| 掉电持久 | ✗ | ✓ |
| 独立上电启动 | ✗ | ✓（产品必需） |

开发期建议双轨：DEV boot 为主快速迭代，flash boot 做阶段性冷启动 +
RISAF 解锁验证。

## 理由

flash 启动**技术可行、风险可控（可逆、不烧熔丝、有 DFU 安全网）、且是产品
掉电稳定启动的必选项**。同时它是解锁 RISAF 受限的 DMA/NPU 功能的唯一现实
路径——这些能力在 DEV boot 下无论怎么改驱动都被硬件防火墙拦截（见
[[hw-stm32n6-gpdma-sram-blocked-dev-boot]]、
[[hw-stm32n6-risaf-dma2d-grantable-gpdma-not]]）。

先做阶段 0 探针而非直接写 FSBL，是因为 flash-boot 默认 RISAF 策略未文档化，
证伪它能以最小代价决定后续是否需要自定义 FSBL 这个大工程。
