# ADR-015: 看门狗（IWDG/WWDG）

## 状态

Done

## Phase

P1

## 目标

> GitHub Issue: #20
> 验证级别: MEASURED

实现 STM32N6 看门狗驱动，支持独立看门狗（IWDG）
和窗口看门狗（WWDG），防止软件死锁导致系统挂起。

## 上下文

STM32N6 有 2 种看门狗：
- IWDG：独立看门狗，使用 LSI 时钟，不受主时钟影响
- WWDG：窗口看门狗，使用 APB 时钟，有精确喂狗窗口

DS14791 Section 34: IWDG/WWDG。
看门狗是嵌入式系统可靠性保障的关键组件。

## 决策

实现 IWDG 与 WWDG 两个看门狗，均通过 NuttX watchdog 上下半框架
（`drivers/timers/watchdog.c`）注册为字符设备，由用户态经 ioctl 驱动：

- **IWDG → `/dev/watchdog0`**：LSI ~32kHz 时钟，独立于主时钟。预分频
  4<<PR（PR 0..6），12-bit 重载（RLR_MAX=0xfff）。`settimeout` 自动挑选
  覆盖请求超时的最小预分频；一旦启动无法停止（无禁用键，`stop` 返回
  `-ENOSYS`），与 STM32H7 参考实现一致。PR/RLR 写保护，写后轮询 SR 的
  PVU/RVU 传播位（有界超时，禁止死等）。
- **WWDG → `/dev/watchdog1`**：APB1 时钟（PCLK1/4096/(1<<WDGTB)）。7-bit
  递减计数器，窗口寄存器 W 置最大（0x7f）以禁用窗口约束，退化为普通超时
  看门狗，超时仅由 WDGTB 时基预分频调节。开启早期唤醒中断（EWI），在复位
  前一个 tick 触发，用于支撑 watchdog 框架的可选 `capture()` op——用户可
  注册一个"复位前告警"回调（cmocka drivertest_watchdog 的 api 用例即用它）。
- **复位原因（reset-cause）**：新增 `board_reset_cause()`，读取 RCC 复位状态
  寄存器的粘滞志映射到 `BOARDIOC_RESETCAUSE_*`，并经 RMVF 清除，供
  drivertest_watchdog 各用例的 `boardctl(BOARDIOC_RESET_CAUSE)` 前置断言。

两个看门狗都在 `board_bringup.c` 中注册，默认停止，由用户态
`WDIOC_START` 启动，不做自动喂狗——把喂狗策略留给应用层（EdgeSight）。

## 设计

### 模块架构

```
IWDG (独立看门狗)
├── 时钟源: LSI ~32kHz
├── 预分频器: 4/8/16/32/64/128/256
├── 重载值: 12-bit (0-4095)
├── 超时范围: ~0.1ms ~ 32s
└── 特性: 独立于主时钟, 一旦使能无法禁用

WWDG (窗口看门狗)
├── 时钟源: APB (经过分频)
├── 窗口值: 7-bit
├── 计数器: 7-bit
└── 特性: 有精确喂狗窗口, 可产生早期中断
```

### NuttX 框架对接

```
NuttX watchdog 框架:
  watchdog_register("/dev/watchdog0", &iwdg_dev)
    → open("/dev/watchdog0")
    → ioctl(WDIOC_SETTIMEOUT, &timeout)
    → ioctl(WDIOC_START)
    → 定期 ioctl(WDIOC_KEEPALIVE) ← 喂狗

自动喂狗 (board_bringup.c):
  board_wdog_init() → 启动看门狗
  work_queue() → 定期喂狗
```

## 真机 MEASURED 验证

> 验证平台: 真实 STM32N647（two-hop SSH + ST-LINK GDB + 串口）
> 验证日期: 2026-07-28
> 脚本: `scripts/hw-verify-watchdog.sh`（本地不入库/gitignore）

**为何不能直接用 cmocka drivertest_watchdog**：该测试是跨复位状态机——每个
用例断言一个 `BOARDIOC_RESET_CAUSE`、故意触发看门狗复位，然后依赖板子**从
flash 自动重启**跑下一个用例。本板是 SRAM 引导（固件经 GDB 载入 SRAM，掉电
即失），任何复位后 boot ROM（PC≈0x18003a1a）找不到镜像只会挂起等调试器，
**不会自动重启回固件**，故该 self-loop 无法越过 case 0。

**实测方法**：启动一次固件 → 用 `wdog` 示例应用驱动 IWDG
（SETTIMEOUT 2000ms / START / KEEPALIVE 喂狗 5s）→ 停止喂狗 → 观测复位
（串口在 ~2s 后静默、PC 落入 boot ROM）→ 重新 attach 调试器经 SWD 直读
复位状态寄存器。粘滞复位标志跨复位保留、且 SRAM 镜像已失无固件清除它，
故 SWD 直读即铁证。

**实测结果**（全部 PASS）：
- ping 期间板子存活 5s（`ping elapsed=0..4500`），证明 START/KEEPALIVE 生效
- 停喂后串口静默、PC=0x18003a1a（boot ROM），证明 IWDG 触发了 MCU 复位
- Phase A 清零后复位再读 `RCC_RSR = 0x04400000`，**IWDGRSTF(bit26) 置位**

**真机发现的驱动 BUG（已修复）**：`board_reset_cause()` 原读 **HWRSR
(0x30)**，但 STM32N6 上 CPU/调试侧可见的粘滞标志在 **RSR (0x34)**——HWRSR
从 CPU AP 读恒为 0（同一会话 RCC_CR 读值正常，排除 SWD 故障）。此 BUG 只有
真机能抓到：Renode 模型与 cmocka self-loop 都无法暴露。已改读 RSR 并
MEASURED 确认。

## 理由

IWDG 简单可靠，独立于主时钟，适合 EdgeSight 长期无人值守运行场景。
两个看门狗都注册为标准 watchdog 字符设备但默认停止、不自动喂狗，把超时值
与喂狗策略完全交给应用层——比在 bringup 里硬编码一个固定超时更通用，也让
drivertest_watchdog 能自由设定各用例的超时。WWDG 的 EWI 提供"复位前告警"
回调，补齐了 IWDG 没有的 `capture()` 能力，使 watchdog 框架 API 覆盖完整。
